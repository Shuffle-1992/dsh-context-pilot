# 上下文压缩档位、文本锚点与推理表现调查

调查日期：2026-10-26，时间口径为 Asia/Shanghai。  
调查对象：`dsh-context-pilot`，包版本 `0.1.70`，代码基线 `b3c815b`。  
范围：源码、现有运行报告、隔离运行验证与公开研究；不修改插件代码、配置或真实会话，不提交、不推送。本文件是调查交付物。

## 1. 结论

**从 24% 改成 8%，有可能改善实际推理表现，但前提是仍然保住当前任务所需的信息。不存在“上下文低于某个百分比，模型就自动更聪明”的通用规则。**

减少过长上下文和无关历史，可能降低信息检索、关联和推理的困难；摘要遗漏必要约束、代码细节或失败现场，又可能抵消甚至超过这部分收益。应追求“足够且相关的上下文”，而不是最小百分比。

对这个插件，建议的选择顺序是：

1. 能明确定位当前任务的起点，且更早的必要依赖已经有可靠记录时，优先按语义锚点保留。
2. 当前任务独立、近期所需信息较少时，考虑深压 8%。
3. 边界不明确时，保留标准 16% 作为折中。
4. 正在跨文件联调、排查复杂问题，确实依赖较长的原始记录时，浅压 24% 有合理价值。

**不建议直接把所有场景强制改为 8%。应先解决决策卡的信息一致性，再比较不同策略的任务成功率。** 本次调查没有开展模型质量 A/B 实验，不能给出 8% 相对 24% 的收益百分比。

## 2. 项目里的百分比到底表示什么

### 2.1 它是近端保留预算，不是最终总占用

默认档位定义见 [compact-range.mjs](../plugin/compact-range.mjs)：

| 中文档位 | 内部兼容 ID | 默认比例 | 1M 窗口下名义保留预算 |
| --- | --- | --- | --- |
| 深压 8% | `light` | 0.08 | 80,000 token |
| 标准 16% | `standard` | 0.16 | 160,000 token |
| 浅压 24% | `heavy` | 0.24 | 240,000 token |

这三个档位主要改变保留范围，不代表三种不同质量的摘要模型或三种推理强度。

最终请求仍包含保留原文、历史摘要、系统指令、工具定义及其他上下文开销。因此“选择 8%”不等于“压缩后表盘一定是 8%”。

还需注意两个实现细节：

- 档位预算会经过上下限夹取，名义下限为 40k，上限为窗口的 50%。在 128k 窗口的隔离验证中，默认三个档位都被抬到 40k；因此不能把档位名字直接当作所有模型上的实际比例。
- [m3.compact.mjs](../plugin/m3.compact.mjs) 的 `scaleRetainBudget` 会用测量折算因子调整按比例路径的预算。真实报告中一次 24% 压缩的名义预算是 240,000，因子为 1.48，范围选择使用的启发式预算为 162,162。两个数字口径不同，不代表偷偷改成另一个档位。

本地一条可以对应上的样本：2026-10-26 14:10 的 24% 压缩，完成时报告占用为 36.9%，随后稳定回落记录为 272,818 token；在该次 1M 窗口中约为 27.28%。不能把压缩完成瞬间的过渡读数当成稳定结果，也不能把历史样本预测值当成本次实报。

证据：[运行报告](../plugin/.data/m1-report.json)、[稳定回落样本](../plugin/.data/settle-drop.json)。这些文件属于本地运行数据，可能未纳入 Git，且后续会滚动更新；本报告中的摘录固定了本次调查使用的事实。

### 2.2 低占比不会自动增加推理强度

压缩档位和 `set_reasoning_effort` 是不同控制项。腾出上下文空间，不意味着自动提高思考强度或自动获得更多推理 token。

同样，1M 窗口的 8% 名义上仍有 80k token，不能与另一个模型小窗口的 8% 等同。质量评估应关注实际输入长度、信息构成和模型版本，而不只看占用百分比。

压完后上下文还会继续增长。因此只改变保留档位，不改变压缩时机，也不意味着后续全过程都处于低占用。

## 3. 实际记录：偏向 24% 成立，精细压缩并非零次

读取了本地报告保留的 120 个快照，覆盖 2026-10-24 11:40 至 2026-10-26 16:24 左右。以会话 ID 和事件时间去重，避免把多个快照中的同一次事件重复计数。

| 观察对象 | 结果 | 解释边界 |
| --- | --- | --- |
| 已保存的会话档位偏好 | 16 条：24% 为 11 条，8% 为 4 条，16% 为 1 条 | 是当前偏好分布，不是历次调用频率 |
| 快照中可恢复的工具调用 | 11 次：24% 为 8 次，8% 为 2 次，16% 为 1 次 | 包含只登记档位等动作，不等于已执行压缩数 |
| 可恢复且已执行的主动压缩 | 8 次：按 24% 执行 6 次、按 16% 执行 1 次、按文本锚点执行 1 次 | 是有限快照样本，不是全量会话日志统计 |
| 保存了锚点的会话偏好 | 2 条 | 仅登记锚点不能证明执行成功 |

那次已执行的文本锚点压缩发生于 **2026-10-24 11:57:25**，会话 ID 前缀为 `session-9a611857`：

```json
{
  "acted": true,
  "rangeSource": "own",
  "tier": "heavy",
  "retainSource": "anchor:text-prefix",
  "retainBudget": 40000,
  "anchorTokens": 18818,
  "anchorFailReason": null
}
```

关键是：**记录仍携带 `tier: heavy`，但实际保留来源是文本锚点，预算为 40k，并非 240k。** 只统计档位字段或只看“浅压24%”标签，会把精细压缩误算成按比例压缩。

因此，对用户观察的准确修正是：“Agent 大部分情况下倾向 24%，精细压缩使用较少；当前本地证据至少能确认一次文本锚点真正生效。”无法由此判断是否由 Agent 完全自主选择，或是否受到当时用户提示的影响。

## 4. 为什么 Agent 容易选 24%

以下分为代码事实和行为解释；行为解释尚未经过控制实验，不能当作已证明的因果关系。

### 4.1 提示对 24% 的适用场景描述很宽

[compact-tool.mjs](../plugin/compact-tool.mjs) 的决策卡把浅压描述为适合“多文件联调/长推理链”，把深压描述为“近端细节不再需要/要预留大量空间”。一般开发任务很容易符合前者，却很难让模型确信“近端细节不再需要”。

当前文案已经加入了多留和少留的成本对比，不能说它完全没有对称提示。但仍有这些选择倾向：

- 24% 被强调为“近端保真最好”。
- 8% 的代价是明确、即时的信息摘要化；减少长上下文对任务质量的潜在好处没有对应的质量反馈。
- 按比例模式的例子直接使用 `tier 浅压24%`，可能产生示例偏向。
- 虽然卡片写了“锚点优先”，但选锚点需要识别任务边界，并判断边界之前有没有必要依赖，决策负担高于选档。

推断：在没有质量反馈的情况下，模型容易把“尽量别丢细节”当作保守策略。经常选择 24% 不能证明它已经比较过 8% 并确认 24% 更优。

### 4.2 档位具有持续沿用效应

选档是会话级持久偏好；后续不传 `tier` 会沿用已有值，而不是重新判断或回到 16%。这有助于保持用户意图，但也会让一次 24% 的选择持续影响后续任务。

与之不同，工具调用不传 `keepFrom` 会清除原有锚点。二者的省略语义不同：

| 省略参数 | 行为 |
| --- | --- |
| `tier` | 沿用已登记档位；从未登记时用标准档 |
| `keepFrom` | 清除已登记锚点 |

这也是精细模式不容易持续使用的一个机制因素，但本次没有统计“忘记重传锚点”造成的实际次数。

## 5. 已确认问题：决策卡预算与实际策略不一致

### 5.1 按比例模式的问题

调用链中的根因明确：

1. [m2.inject.mjs](../plugin/m2.inject.mjs) 第 233 行附近的 `retentionTeach(win)` 读取 `getRangeApi()?.RETAIN_RATIO`，其常量为 0.16。
2. `renderPolicyCard` 用这组数生成“现行生效预算”，同时另行读取会话档位，生成当前档位标题。
3. 实际压缩执行则按会话档位调用 `resolveTier`。

因此会出现同一张卡中“当前档位24%”与“现行保留16%”并存。真实运行报告已经出现此现象；独立运行原始渲染函数得到：

| 已登记档位 | 执行侧名义预算，1M 窗口 | 卡片标题 | 卡片现行预算 |
| --- | --- | --- | --- |
| 深压 8% | 80k | 深压8% | 160k / 16% |
| 标准 16% | 160k | 标准16% | 160k / 16% |
| 浅压 24% | 240k | 浅压24% | 160k / 16% |

这会影响“本档会摘要多少内容”等相关说明的可信度。**这是已复现的信息错误，但它对 Agent 选择 24% 的影响有多大，尚未量化。**

### 5.2 文本锚点也是同样问题吗？

**决策卡显示：是，而且还缺少当前已登记锚点的状态展示。实际范围执行：不能据此判定同样出错。**

当前 `renderPolicyCard` 没有读取并传递本会话的 `getAnchor(sid)` 或解析结果。卡片会介绍锚点的通用用法，却不会据已登记锚点给出当前预算，仍显示档位标题和上述 16% 的现行预算。

针对文本锚点的独立运行验证使用原始模块、内存模拟会话，不接入真实 DSH 会话，也不写入偏好文件：

| 项目 | 实测结果 |
| --- | --- |
| 登记的文本锚点 | `新需求：独立模块调查` |
| 保存的备用档位 | `heavy`，浅压24% |
| 文本定位 | 成功，`text-prefix` |
| 锚点到末尾的测量量 | 30k |
| 余量和下限处理后的预算 | 40k |
| 范围选择实际保留 | 40k，锚点及其后内容被保留 |
| 卡片当前档位 | 浅压24% |
| 卡片现行预算 | 160k / 16% |
| 卡片是否展示已登记的具体锚点文本 | 否 |

上述模拟验证与第 3 节的真实执行记录相互支持：**文本锚点能力在正常自选范围路径上可以工作；问题在于决策前的展示没有反映它。**

### 5.3 文本锚点的实际边界

- 文本按“前缀优先、包含匹配回退”定位真人用户消息；同类匹配取最近的一条。短而重复的片段可能定位到非预期消息，应选具有辨识度的任务开头。
- 粒度是整条用户消息，不是消息内部的字符范围，也不是对任意旧片段做选择性压缩。锚点之后即使有无关内容，也会一起保留。
- `recentUser:1` 指最近一条用户消息，不等于当前任务起点。最近一句若只是“继续”，从这里保留未必能覆盖此前的任务要求。
- 锚点预算不经过档位折算；`keepFromSeq` 在自选范围路径上保护锚点。预算下限、余量、消息边界和工具配对可能让保留范围比锚点严格起点更早。
- 文本未命中时，可退到 `recentUser`，再退到档位。应查看回执中的实际来源和失败原因。
- “锚点之后原样保留”的保障有执行路径边界：强制线下的范围异常通常收手；越线兜底以及自选压缩后仍越线的收口可能走官方 `context-overflow`，不能把正常 `own` 路径的锚点保障扩展到这些路径。

执行检查应联合看 `state/acted`、`retainSource`、`rangeSource`、`anchorFailReason` 和实际保留范围。仅有 `tier: heavy`，甚至仅有 `retainSource: anchor:*`，都不足以证明最终全过程按锚点范围完成。

## 6. “上下文越少，推理越强”的研究依据与限制

### 6.1 有实证支持减少不必要的长上下文

- **Lost in the Middle（TACL）**：相关信息在长输入中的位置会影响问答和检索表现，位于中间时更容易出现性能下降。它证明长窗口不等于均匀利用所有信息，并不证明 8% 是最佳阈值。[论文](https://arxiv.org/abs/2307.03172)
- **Context Rot（Chroma，2025）**：在 18 个模型和多种受控任务上观察到输入增长带来的可靠性下降；作者也说明这些任务不能覆盖全部真实应用，且没有给出确定的机制解释。[原始报告](https://www.trychroma.com/research/context-rot)
- **Context Length Alone Hurts LLM Performance Despite Perfect Retrieval（EMNLP Findings 2025）**：在数学、问答和编码实验中，即使相关信息能够被正确取回，输入变长仍可能降低表现。不能把所有长上下文问题都归结为“没有找到关键信息”。[论文](https://aclanthology.org/2025.findings-emnlp.1264/)
- **Anthropic 的上下文工程经验**：建议寻找足以完成任务的最小高信号上下文集合；同时明确“最小”仍必须包含充分信息。[原始文章](https://www.anthropic.com/research/effective-context-engineering-for-ai-agents)

### 6.2 不能直接推导这个插件应始终使用 8%

研究大多比较不同长度、信息位置或干扰内容，并未直接比较本插件对同一 DSH 会话做 8% 与 24% 有损摘要后的编码成功率。

本地近期路由记录包含 `deepseek-v4.1-flash`。上述跨模型研究不能直接给出该模型在当前 provider、当前摘要策略下的 8%/24% 优劣曲线；第三方路由名也不足以验证其精确权重修订。

此外，DeepSeek-V4.1-Flash 技术报告中的 KV cache 压缩属于模型内部计算和存储设计，与插件把历史对话变成摘要是两个层面的机制，不能把前者的结果当作后者的质量验证。[官方技术报告](https://arxiv.org/abs/2609.19969)

合适的表述是：**在任务所需信息充分保留时，缩短不必要的上下文有望改善模型的实际推理表现。** 不宜表述为“释放的上下文会直接变成智力”或“8% 必然比24%更强”。

## 7. 当前可采用的使用建议

| 情况 | 建议 | 理由 |
| --- | --- | --- |
| 新任务与旧任务基本独立，起点清晰 | 优先文本锚点，必要时提供备用档位 | 按任务边界保留更贴近信息需求 |
| 当前任务所需资料集中、可从文件重读，边界不易精确指定 | 可以试 8% | 压掉大量无关历史的收益更可能超过损失 |
| 同一任务持续推进，但对依赖范围拿不准 | 16% | 比一律选极端档位更稳妥的起始策略 |
| 多文件联调、复杂排错、未固化的设计推导，仍需大量原始细节 | 24% 或较早的任务锚点 | 避免关键证据过早只剩摘要 |
| 要进入困难推理阶段 | 先确认关键约束、证据和未决问题，再决定压缩 | 推理任务困难不等于必须多留，也不等于必须少留 |

可以对 Agent 使用以下决策要求，作为后续策略实验的候选文案；本次没有写入插件配置：

> 先确定当前任务还依赖哪些原始信息，以及当前任务的最早必要起点。能可靠定位时优先按该起点保留；边界之前仍有必要约束时先确认其已有可靠记录。不能定位时再选择档位：信息需求较少用深压，依赖范围不明用标准，确实需要较长原始记录用浅压。选择浅压时说明需要保留的具体内容；压缩后依据实际执行回执确认来源和结果。

不要机械规定“每次优先 recentUser:1”，也不要仅凭“要进行复杂推理”就固定选 8% 或24%。

## 8. 后续优化与 Simplify 建议，仅提出不实施

### 8.1 先修事实一致性，再调整模型选择偏好

| 事项 | 结论与建议 | 本次状态 |
| --- | --- | --- |
| 当前档位与预算不一致 | 决策卡应从当前会话实际策略派生预算，不能固定读取默认比例 | 已复现，未修复 |
| 当前锚点状态不可见 | 分别展示当前保留模式、具体锚点、预计预算及备用档位；解析失败要明确显示回退 | 已复现，未修复 |
| 预算与总占用混用 | 分开呈现近端预算、摘要/固定开销、当前实测及预计稳定值 | 已审查，建议项 |
| 对 24% 的提示偏向 | 要求说明仍需保留的具体信息，并用质量数据检验选档策略 | 有机制依据，因果未量化 |
| 缺少质量反馈 | 目前记录能证明调用、执行、token 变化，不能证明推理提升 | 需要后续任务级实验 |

### 8.2 强制性优化的三个维度

- **性能**：优先减少重复、无关的历史和提示；评估端到端耗时、重读次数、摘要成本及缓存影响，不能只优化压缩后的 token 数。
- **安全**：保持现有消息边界、工具调用配对和真人消息识别的保护；关键权限约束不能仅因变旧就被视作无关信息。本次没有新增 API 或权限，也未进行完整安全渗透测试。
- **健壮性**：预算、当前模式和执行回执保持一致；锚点未命中、预算夹取、官方兜底及过渡读数应可区分，避免错误承诺。

### 8.3 Simplify

建议把模型的决策顺序收敛为两步：“能否确定必要上下文的起点”→“不能确定时再选比例”。展示上分清当前模式与备用档位，减少相互重复或矛盾的说明。

不建议先增加更多比例档位、更多强制提醒或新的独立压缩工具。现有能力已覆盖主要选择，当前优先事项是正确展示、减少决策歧义和验证实际收益。

## 9. 如何验证 8% 是否真的更好

这是一项建议实验，**本次未执行真实模型 A/B，也未产生相关模型调用费用**。

1. 从真实任务中选取若干压缩前快照，至少覆盖“独立新任务”“复杂连续排错”“较多旧约束”三类。
2. 从同一压缩前状态分别运行 8%、16%、24% 和语义锚点策略。不要先压24%再压8%，否则历史已不同。
3. 固定模型版本、provider、思考强度、采样参数、工具、后续问题和摘要配置；压缩时不要顺带换思考档位，否则无法归因。
4. 对每组进行重复，考虑推理和摘要本身的随机性。先小样本试验，再决定是否扩大。
5. 用可核验结果评价：功能测试通过率、遗漏约束数、重复犯错数、重新读取工具的次数、完成耗时、输入输出及摘要总成本。
6. 记录实际请求长度与压缩路径，区分按档位、按锚点、官方兜底；等待 provider 刷新后读取稳定占用，不拿表盘过渡值比较。

优先级应是任务正确性和约束遵守，其次才是成本和耗时。只有在同类任务上成功率没有恶化或有所提升，才能把更深压缩作为有证据的策略，而不是以更低占用率代替质量结论。
